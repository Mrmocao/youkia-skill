# 本次遇到的问题与处理

## 1. 没有确认表单，却返回拒绝

**症状：** `The approval was declined, so imagine did not run.` 用户明确表示没有看到带 Approve 的表单。

**本次已确认原因：** 当前聊天有效 `approval_policy=never` 自动拒绝了 MCP 的非空 elicitation 表单。`MIDJOURNEY_CONFIRM=human` 请求的必填布尔 approve 因此没有展示。它不是 Midjourney 内容审核、额度不足或登录失败，也不能推断用户手动点了拒绝。

**处理：** 查看当前聊天实际审批策略和客户端 elicitation 支持。用户将当前聊天切换为允许询问的模式（本次为 on-request）后保留 human，重新验证。产品中的“默认权限”“完全访问”等标签因版本而异，不保证与某个策略一一对应。找不到选项时先读取当前版本文档或可见 UI，不编造设置位置；不擅自全局放宽权限。

切换权限本身不证明链路修好，应区分“设置已切换”和“确认传输已验证”。新聊天可能采用其他策略。客户端不支持对应表单时明确报告兼容性限制。

**禁止的处理：** 设置 model 模式来消掉拒绝、自动勾选、修改源码伪造 accept、偷偷改用 CLI `--confirm`。用户明确拒绝或取消时停止。另行授权的 CLI 单次任务是独立操作，不能宣称 MCP 已修好。若是自动审批审查阻止了工具，应原样说明阻止动作和理由，不改通道规避。

## 2. 弹出表单并提交，仍然拒绝

检查是否真正勾选 Approve。2.0.1 的 approve 默认 false；accept 但未勾选也应停止。不要把这个防误操作机制改成自动批准。

## 3. 日常 Chrome 已登录，MCP 却显示未登录

查看 MCP 连接的是哪个 CDP 端点和专用 profile。只看到用户的普通网页 URL 不代表可以附着其浏览器。本次日常 Chrome 没有调试端口，该 MCP 也没有浏览器扩展桥接能力。解释专用目录需要再次登录同一账号，不需要新账号；不要复制 Cookie、读取令牌或克隆日常 profile。

若用户已有可用专用 CDP 会话，先复用，不再新建窗口。检查端口冲突与 profile 占用，不终止用户无关浏览器进程。

## 4. 误把 127.0.0.1 调试地址当登录页

CDP_URL 是程序连接入口，登录应在受控 Chrome 的 https://www.midjourney.com 页面完成。不要引导用户在调试地址输入账号信息。

## 5. whoami 报 browser_running:false

2.0.1 的 whoami 不负责自动启动 Chrome。先区分浏览器没启动与已启动但失去登录。允许自动启动时运行 login 或一次可启动浏览器的只读查询，再检查；不要据此断言用户的日常浏览器账号退出了。

## 6. 首次只读查询出现 URL 解析错误

**实测症状：** `Failed to execute 'fetch' on 'Window': Failed to parse URL from /api/user-queue`。

本次出现在 Chrome 冷启动、目标页面尚未加载完成时。确认受控页面已到正确站点并就绪，再重试该只读检查一次。如果仍失败，记录页面状态和错误，检查当前版本实现。不能把这个经验套用到所有网络错误，尤其不能据此重提生成任务。

## 7. 修改配置后仍看不到生成工具

区分源文件已修改与服务器进程已重载。核查实际配置路径、覆盖项和当前客户端使用的 Node/入口。必要时重启客户端并在新聊天查询工具列表。只读模式会隐藏非只读工具；启用需同时核查 READ_ONLY=0 和 ALLOW_DESTRUCTIVE=1。

2.0.1 的本次安装观测到只读 17 个、完整 32 个工具，其中 10 个有消费确认。数量只用于版本记录，不适合作为其他版本的硬性验收条件。

## 8. 生成长时间没有结果

超时不等于拒绝。get_queue 确认排队状态，查询已有任务并继续等待或下载；账号并发限制和 relax 排队都可能延长耗时。若提交响应丢失且找不到 ID，核对近期任务、时间和提示词，无法确认是否接受时告知用户不确定性，不自动补单。

## 9. 登录、网站验证或额度限制

signed_out、Cloudflare、401/403 等必须结合实际返回判断。需要登录或验证时交给本地浏览器，不索取验证码，不绕过网站机制。额度不足或速率限制时停止消费请求，告知用户实际原因；不切换账号、批量重试或推测付款状态。

## 10. 电脑控制提示“无法可靠识别 Chrome 当前网址”

这段用户转述提示疑似发生在电脑控制通道，不能仅凭自然语言回复断定真实工具错误或系统拒绝来源。先查看出错工具名、脱敏原始错误、客户端与技能版本，以及该会话是否发现 Midjourney MCP 工具。它不能证明 Midjourney 账号掉线或图片内容被拒绝。没有同事环境的日志时，明确标注未复现，不把本机成功推广到对方电脑。

处理顺序：

1. 停止电脑控制重试，不让它猜测标签页或盲目上传。
2. 可独立核对 MCP 的工具发现、CDP_URL、专用 profile 和只读状态；若系统阻止了具体动作，不用 MCP、CDP 或 CLI 重新执行该动作来绕过阻止。
3. 如果用户只是要使用原图，检查 `imagine` schema 是否有 `image_prompts`。2.0.1 有该参数，但只接收直接图片 URL或 Midjourney `s.mj.run` URL，没有本地文件上传工具。
4. 对未被阻止的独立素材准备流程，可指导用户在专用 Chrome 的 `https://www.midjourney.com` 页面手动上传原图，取得网站提供的实际图片资源 URL；不要将其作为自动审核拒绝后的绕行。不要让用户在 `127.0.0.1:<port>` 调试地址登录。
5. URL 仍不可获得时停止并报告能力边界；不要用本地路径、网页详情 URL、猜测 URL 或重复生成替代。

电脑控制错误与 MCP 确认拒绝是两类独立故障：前者是浏览器自动化入口被安全停止，后者才是 `approval_policy`/elicitation 流程。分别记录，避免把“Image Prompt 上传失败”描述成“生成被拒绝”。

## 最小诊断记录

记录时间、包版本、Node/Chrome/客户端版本、浏览器是否运行、只读接口成功与否、有效审批策略、是否出现表单、错误阶段，以及是否可能已提交。共享记录必须去除账号 ID、真实任务 ID、私有图片 URL、个人路径和会话信息。不要上传原始浏览器日志、profile、全局配置或配置备份。
